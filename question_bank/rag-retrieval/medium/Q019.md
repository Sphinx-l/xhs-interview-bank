# Q019 · RRF 的全称和作用是什么？它与 Rerank 有什么区别？为什么 RAG 流程要引入父子索引？

RAG 检索与知识组织 · 中 · `RRF` `Rerank` `父子索引` `召回重排`

> 真题来源：虾皮 · Agent 开发 · 一面/二面 · 同题另见 2 处（发帖人自述，未核实）

## 背景描述

这道题把 RAG 检索层的三个易混概念放在一题里考：融合（RRF）、精排（Rerank）、索引组织（父子块），用来区分背词与理解。

## 引出的痛点

把 RRF 当成排序模型、把 Rerank 当成融合方法，或者不知道父子索引解决的是『检索粒度与生成粒度冲突』，都会在这题暴露。

## 考点

RRF 的定义与公式、Rerank 的交叉编码精排原理、父子索引的大小块解耦逻辑，以及三者在链路中的位置。

## 思考方向与解题思路

按链路位置逐一讲清三者的输入输出与解决的问题，最后用一条完整链路把三者串起来。

## 推荐答案

RRF（Reciprocal Rank Fusion，倒数排名融合）把多路检索的结果按排名倒数求和合成一个列表，解决的是融合而非精排；Rerank 用交叉编码器对 query 与文档逐对深度打分，解决的是精排；父子索引让检索用小块（父块的片段）保召回精度、生成用大块（完整父块）保上下文完整，解决的是检索粒度与生成粒度的冲突。

- RRF：每文档得分 = Σ 1/(k + rank)，k 常取 60；只依赖各路排名，无需调参、不受各路分数量纲影响；位于多路召回之后。
- Rerank：交叉编码器把 query 与文档拼接后联合编码打分，比双塔向量的独立编码更准但更慢，只能用于小候选集；位于融合之后、取 TopN 之前。
- 分工一句话：RRF 决定『多路候选怎么合并』，Rerank 决定『合并后的候选谁真正相关』。
- 父子索引：子块（小粒度）参与检索匹配，命中后返回其父块（段落/章节级）注入生成——小块保检索精度，大块保语义完整。
- 为什么需要：直接用小块，生成缺上下文（命中半句条款）；直接用大块，向量表征被稀释、检索精度下降——父子结构让两种粒度各司其职。
- 链路位置：多路召回（子块级）→ RRF 融合 → Rerank 精排 → 映射回父块 → 去重组装注入。

## 进阶理解

### RRF 与 Rerank：融合器与精排器

RRF 是结果集融合方法，Elasticsearch 官方定位是『把多个具有不同相关性指标的结果集合成一个，无需调参，各指标间无需相关』：对每个查询路的结果，按文档在该路的排名贡献 1/(k+rank)（rank 从 1 起，k 为排名常数，ES 默认 60），多路求和即最终分。它是轻量算术，不读文档内容、不建模。Rerank 则是内容级精排：交叉编码器（cross-encoder）把 query 与候选文档拼成对输入模型联合编码，直接输出相关性分——因为看见了词级交互，精度显著高于双塔向量的分别编码；代价是每对都要跑一次模型，只能用于几十条候选。因此标准链路是：召回求全（多路）→ RRF 求合（融合）→ Rerank 求准（精排）。

### 父子索引：粒度解耦

RAG 存在一个结构性矛盾：检索希望块小——小块向量表征集中，匹配精度高；生成希望块大——模型需要完整上下文才能正确作答（命中半条条款不知道适用条件）。父子索引的解法：把文档切成父块（段落或小节，几百 token）与子块（父块的更细片段，几十到百余 token）；只有子块建索引参与检索；命中子块后向上取其父块进入候选，注入时给父块。工程要点：父子映射关系建库时写入元数据；多个子块命中同一父块要去重，避免重复注入；父块大小以『自足解释一个主题』为准。这本质是检索粒度与上下文粒度的分离，与『小 TopK + Rerank』解决的是不同维度的问题，常一起使用。

### 完整链路中的三者协作

一条生产级检索链路：BM25 路 + 向量路在子块级各召回 TopK（如 25）→ RRF 融合两路排名得到合并候选 → Rerank 交叉编码器对前 30 条精排 → 取 TopN 的子块映射回父块、去重 → 按分数排序组装注入。三个组件各答一问：RRF 答『两路分数不可比怎么合』，Rerank 答『相似不等于相关怎么精』，父子索引答『检索要小生成要大怎么办』。面试中能把三者的输入输出与失败模式（融合权重失衡、Rerank 候选过多超时、父块切分不当上下文仍碎）讲清，就是完整的检索层认知。

**示例**：合同问答：用户问『违约金上限是多少』，合同条款长段内含一句关键规定。

1. 子块（条款内小片段）在向量路与关键词路都命中，RRF 融合后靠前。
2. Rerank 精排确认该片段与『违约金上限』高度相关，滤掉了仅出现『违约』字样的噪声块。
3. 取该子块的父块（完整条款，含适用条件与例外），注入生成——答案带上了『不超过实际损失 30% 且有例外情形』的完整语境。

观察：没有 RRF 两路打架，没有 Rerank 噪声混入，没有父子索引答案缺上下文——三者缺一，这条链路的质量都会塌一角。
