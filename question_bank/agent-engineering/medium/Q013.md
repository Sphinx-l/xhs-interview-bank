# Q013 · 如何设计工具的描述与参数 Schema，才能提升大模型的调用准确率、减少瞎编参数？

Agent 工程化与运行环境 · 中 · `工具Schema` `参数校验` `工具描述` `防呆设计`

> 真题来源：字节跳动 · AI Agent · 一面（发帖人自述，未核实）

## 背景描述

工具定义质量直接决定调用准确率，Anthropic 称之为 ACI（Agent-Computer Interface）工程；面试官用这道题区分『会接工具』与『会设计工具』。

## 引出的痛点

描述含糊、参数开放自由度过大、缺乏示例与边界说明，模型就会选错工具或编造参数；而把这些责任推给『模型不够强』是错误归因。

## 考点

描述怎么写、Schema 怎么约束、防呆（poka-yoke）怎么做、错误信息怎么回灌形成修复闭环。

## 思考方向与解题思路

按描述层→Schema 层→防呆层→闭环层四层展开，每层给可执行的规则。

## 推荐答案

把工具定义当写给新同事的接口文档：描述层说清用途、边界、示例与易混点；Schema 层用枚举与格式约束收窄生成空间；防呆层让错误难以发生；闭环层把校验失败写成模型可修复的提示回灌重试。

- 描述层：一句话职责 + 适用/不适用场景 + 与相近工具的差异 + 输入输出示例，像给初级工程师的 docstring。
- Schema 层：能用 enum 不用自由 string；日期、ID、路径用 format/正则并给示例；必选可选分明，参数描述写明单位与取值范围。
- 防呆（poka-yoke）：要求绝对路径替代相对路径、用结构化对象替代长拼接串、危险参数拆独立字段。
- 减少格式负担：不要求模型维护行号、精确转义长文本；输出格式贴近自然文本惯例。
- 闭环：校验失败把可读错误（哪个字段、期望什么、实际收到什么）回灌，模型大多能自纠。
- 上线前用探针集（多问法 + 相近工具边界 case）测选错率与参数错误率，迭代描述到达标。

## 进阶理解

### 描述工程：模型唯一的信息来源

模型对工具的全部认知来自 description 与 Schema 文本，因此描述质量就是调用准确率的上限。Anthropic 在 Building effective agents 的工具附录中给出的原则：从模型视角自问『看描述和参数能否不假思索地知道怎么用』；包含示例用法、边界情况、输入格式要求、与其他工具的明确区分；把参数命名与描述改得更显眼；用大量样例输入实测模型犯的错并迭代。一个实用检验：把两个易混淆工具的描述并排给不熟悉的同事看，若同事也会犹豫，模型必然选错——那就继续改写差异说明。

### Schema 约束与防呆设计

Schema 的目标是最小化模型的自由生成空间：①类型收紧——string 能换 enum 就换 enum，数字给 min/max；②格式显式——时间用 ISO8601 并在描述中给示例，ID 说明来源系统与格式；③结构化优先——与其让模型拼一个含分隔符的长字符串，不如拆成多字段对象，减少拼接错误；④消除隐性计数——不要求模型数行号、数字节这类易错操作。防呆设计的经典案例：SWE-bench 实践中把文件编辑工具从相对路径改为强制绝对路径后错误显著下降——不是提示模型小心，而是让错误无法发生。另外工具粒度也影响准确率：一个万能工具带 15 个参数不如拆成职责清晰的三个工具，参数少而专注的工具描述更短、误用率更低。

### 错误回灌与持续迭代

校验失败的处理分两级：格式错误（JSON 解析失败、类型不符）——把错误文本回灌并要求仅重发修正后的 tool_call；语义错误（城市名不存在、日期超范围）——把可用选项或相近匹配回灌，让模型二选一而非重新猜。每类高频错误都应反哺工具定义：同一个参数错误出现三次，就说明该参数的描述或约束有缺陷。建立『探针集 → 调用统计 → 描述迭代』的小闭环，工具定义像 Prompt 一样纳入版本管理与回归测试——这是把工具工程从一次性胶水代码变成可持续资产的做法。

**示例**：天气查询工具最初定义为 get_weather(location: string, date: string)，线上频繁出错。

1. 问题定位：location 出现『北京今天』这种混合语义串；date 出现『明天下午三点』自然语言。
2. 重设计：location 描述改为『城市标准名称，如 Beijing；不含时间信息』；date 改为 format: date, 描述给 ISO8601 示例；新增 unit 枚举字段；同时提供 parse_relative_time 工具分担自然语言解析。

观察：错误率的下降来自把自由生成空间逐项收窄——enum、format、职责拆分，每一项约束都在替模型减少一次猜错的机会。
