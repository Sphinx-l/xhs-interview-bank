# Q014 · 工具库有上百个工具（或几百个用户自定义 Skill）时，如何让模型快速准确地选中工具？召回率下降怎么解决？

Agent 工程化与运行环境 · 中 · `工具检索` `两级加载` `Skill召回` `动态挂载`

> 真题来源：字节跳动 · AI Agent · 二面（发帖人自述，未核实）

## 背景描述

工具规模化管理是 Agent 平台化的分水岭题：小 Demo 全量挂载没问题，规模一大立刻崩坏，考察候选人是否做过真实规模的工具系统。

## 引出的痛点

全量注入上百个工具 Schema 会同时挤爆上下文预算和稀释模型注意力，选错率随工具数上升；用户自定义 Skill 泛化后语义重叠加剧，召回准确率进一步下降。

## 考点

工具检索/两级加载的分层方案、语义重叠与消歧、召回效果的评测指标。

## 思考方向与解题思路

先讲『全量挂载为什么不行』的量化原因，再给检索式两级加载架构，最后讲重叠消歧与评测闭环。

## 推荐答案

把工具选择从『模型在一堆 Schema 里挑』改造成『先检索后加载』：轻量目录做一级召回筛出候选子集，仅展开候选的完整 Schema；配合描述消歧、命名空间过滤与召回评测，百级工具与用户自定义 Skill 都能稳定工作。

- 全量挂载双重失败：百级工具 Schema 占数万 token；工具越多、同义工具越多，选择准确率越低。
- 两级加载：目录（名称 + 一句话描述 + 元数据）经向量 + 关键词双路召回 Top10-20，仅展开候选完整 Schema 注入本轮请求。
- 动态挂载：按业务域与权限预筛、MCP Server 按需连接；提供 search_tools 元工具让模型主动检索扩展。
- Skill 召回治理：语义重叠的做描述差异化与合并；类别命名空间过滤；高频错分对写对比式描述，必要时加规则/意图分类兜底。
- 评测三件套：目录召回率、最终选择准确率、平均注入 token；用线上 trace 挖错分 case 回流评测集。

## 进阶理解

### 为什么不能全量挂载

两个代价随工具数增长：token 预算上，一个中等复杂度工具的 Schema 约百余 token，数百个工具即数万 token，吃掉小半窗口；效果上，工具清单本质是模型的多分类标签集，类别越多边界越模糊——尤其存在同义工具（两个都能查订单）时，模型选择会被描述措辞的细微差异主导而不是任务语义主导，Anthropic 亦特别提醒在使用许多相似工具时，工具之间的差异描述是影响效果的关键。结论：工具规模明显超出数十个后就应引入检索式管理，这与 RAG 解决『知识太多不能全塞』是同一思想在工具层的映射。

### 两级加载与动态发现

工程架构：①离线为每个工具建立检索条目（嵌入其名称、描述、示例 query），可用用户 query 的向量 + BM25 关键词双路召回并融合；②在线每轮（或每任务开始时）检索 TopN 候选，仅展开候选的完整 Schema；③补充主动发现通道——提供一个 search_tools(query) 元工具，模型在候选集不含所需能力时自主检索扩展，兼顾覆盖率与预算；④按权限与业务域过滤（namespace/tenant），既省空间也防越权。注意候选集不是越大越好：注入 15-20 个高质量候选的选择准确率通常优于 50 个含噪候选。

### Skill 重叠治理与评测

用户自定义 Skill 的特有问题是语义漂移与重叠：几百个 Skill 中『周报生成』『工作总结』『日报汇总』语义高度接近，检索侧互相挤占 TopN。治理手段：①入库时做相似度检查，提示创建者复用或明确差异化；②描述中强制写『适用场景 + 不适用场景 + 与相近 Skill 的区别』；③类目树 + 标签过滤先缩小池子再做向量排序；④错分监控：线上统计『检索命中但模型弃选』与『模型选了非 Top1』的比例，定位需要改写描述的 Skill。评测指标三件套：目录召回率（正确工具进候选集的比例）、最终选择准确率、平均注入 token——前两者管效果，后者管成本，三者一起防止『为准确率无限扩大候选集』的过拟合做法。

**示例**：示意场景（假设数字）：企业 Agent 平台聚合数百个工具与大量用户自定义 Skill，覆盖多个业务域。

1. 改造前（示意）：全量挂载挤爆上下文预算，按域裁剪后不同域工具又互相挤占候选位，错选频发。
2. 改造：按业务域拆 namespace 并做权限过滤；每轮检索目录 Top15（向量+BM25 融合）；模型需要时调 search_tools 扩展；对语义重叠的『周报类』Skill 重写差异化描述。
3. 验证口径：上线前后对比目录召回率、选择准确率与平均注入 token 三项指标，确认『更少但更准的候选』确实优于全量挂载。

观察：工具规模化管理的本质是把『选择问题』拆成『检索问题 + 小规模选择问题』，每一段都可独立优化与评测。
