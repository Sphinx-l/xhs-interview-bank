# Q020 · 文档为什么要切片？Chunk Size 和 Overlap 如何确定？为什么不能只用固定长度切分？递归/结构化切分好在哪里？

> 真题来源：字节跳动（抖音） · Agent 开发 · 一面 · 同题另见 4 处（发帖人自述，未核实）

## 背景描述

切分是 RAG 入库侧的基础题，考察对『块大小决定检索精度与上下文完整性平衡』的理解，追问常落在 size/overlap 的确定方法。

## 引出的痛点

拍脑袋给 512/50 的固定切分会让表格被打散、条款被腰斩、语义被切在边界——检索命中的块要么缺上下文要么全是噪声。

## 考点

切分必要性与取舍逻辑、size 与 overlap 的确定依据（内容类型+模型窗口+评测）、固定长度切分的失败场景、结构化/递归切分的改进。

## 思考方向与解题思路

先讲为什么必须切与切分目标，再给 size/overlap 的确定方法，然后列举固定切分的失败场景，收尾给按文档类型的选型表。

## 推荐答案

切分是因为 Embedding 窗口有限且长文本向量表征被稀释、注入预算也有限；Chunk Size 由内容类型与 Embedding 模型窗口共同决定，Overlap 防止关键句被切断在边界；固定长度切分会打散表格、腰斩条款、切碎语义，应优先按文档结构（标题/段落/表格）切分，递归字符切分做兜底。

- 为什么切：块要足够小以保检索精度与低延迟，又足够大以承载完整语义——切分的本质是在两者间找平衡。
- Size 确定：以 Embedding 模型的有效窗口为上界，按内容类型定（FAQ 类 100-256 token，条款/说明文 256-512，需上下文的场景用父子索引），最终靠评测集对比召回率定档。
- Overlap 确定：通常为 chunk 的 10-20%，作用是让跨边界的句子在相邻块中至少完整出现一次；过大则重复块增多浪费预算。
- 固定长度失败场景：表格从中间截断行列错乱、条款的适用条件与正文分家、代词指代的句子与先行词分块。
- 结构化切分：按标题层级、段落、表格整体、代码块等语义边界切，保住信息单元完整；Markdown/HTML/代码可利用标记语言结构。
- 递归字符切分：按分隔符优先级（段落→句子→词）逐层降级，尽量在自然边界断开，是无结构文本的默认兜底。

## 进阶理解

### 切分的取舍逻辑

Pinecone 对切分的经典表述：chunking 是把大文本拆成较小片段的预处理技术，目标在『足够大以包含有意义的信息』与『足够小以支撑高性能低延迟』之间找平衡。三个约束共同决定块大小：①Embedding 模型——有最大输入窗口，且超出有效长度后向量表征质量下降（长文档细节被平均化）；②检索精度——块越大向量越『泛』，匹配越不锐利；③生成注入——TopK 块要一起放进提示，块大则 K 必须小、覆盖面窄。因此确定 size 的正确姿势不是抄一个数字，而是：定内容类型 → 参考模型窗口定候选区间 → 用评测集（含边界 case）对比不同档位的召回率与最终回答质量。

### Overlap 与固定切分的坑

Overlap 让相邻块共享一段尾部/头部文本，被切断在边界处的关键句至少会在其中一个块里完整出现，代价是存储与检索的重复。经验值 10-20%，具体以『最长语义单元（如一条完整条款）能被 overlap 覆盖』为准。固定长度切分的问题清单：表格从中间截断（行列对应关系全毁，检索命中也无法解读）；条款的条件句与主句分家（『不超过 X，但有下列情形除外』被切成两块）；对话/叙述文中代词与其先行词分块（『该产品』没了所指）。这些失败共同指向一个结论：切分点应落在语义边界上，而不是字符计数上。

### 结构化与递归切分

结构化切分利用文档自身结构：Markdown/HTML 按标题层级聚段，PDF 解析出的章节、列表、表格作为不可分割单元（表格整块转结构化文本），代码按函数/类边界切。这是首选——结构边界天然就是语义边界。递归字符切分处理无标记文本：按分隔符优先级（\n\n → \n → 句号 → 空格）逐层尝试，在不超过上限的前提下尽量在高层边界断开，兼顾自动化与语义完整。进阶手段：语义切分（用 Embedding 相似度检测主题断点）、父子索引（小块检索大块注入）、以及人工/规则干预切分（对高价值文档手动标注不可分割单元）。评测永远闭环一切：同一份语料跑不同切分策略的召回率与端到端回答质量，数据说话。

**示例**：产品手册同时含 FAQ 短条目、长篇配置说明与大规格表。

1. 错误做法：统一 256 token 定长切分——FAQ 两条挤一块互相污染，规格表第 5 行后被截断。
2. 分层策略：FAQ 按问答对逐条切（小块高频命中）；配置说明按小节切（256-512，overlap 15%）；规格表整体一块并转 Markdown 表格、配字段说明元数据。
3. 验证：评测集中『查某参数』类 query 命中率显著回升，表格类 query 不再返回断裂行。

观察：切分策略跟着内容类型走而不是一刀切，且必须用评测集验证——这是入库侧最重要的一条工程纪律。
