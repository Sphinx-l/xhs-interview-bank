# Q004 · Agent Loop 的核心流程怎么设计？什么时候停？怎么防死循环与重复调用？终止后如何校验结果？

AI Agent 架构设计 · 高 · `Agent Loop` `终止条件` `死循环检测` `结果校验`

> 真题来源：字节跳动 · Agent Harness · 一面 · 同题另见 3 处（发帖人自述，未核实）

## 背景描述

Agent Loop 是 Harness 的心脏，面试官会沿『循环结构→终止条件→异常处理→结果信任』逐层追问，考察候选人是否真正在生产环境维护过失控的循环。

## 引出的痛点

循环没有多档终止与死循环检测，线上会出现 token 烧穿预算、任务永不结束、模型自称完成但实际没做完三类事故。

## 考点

单轮循环的组成、多维度终止条件、死循环与重复调用的检测手段、『模型说完成了』之后的校验。

## 思考方向与解题思路

先给出循环骨架，再分层讲终止与防抖机制，最后讲结果校验与兜底，形成完整生命周期叙述。

## 推荐答案

Agent Loop 每轮执行『构造上下文→模型推理→解析工具调用→校验执行→结果回灌→终止检查』；终止靠硬限（轮数/token/耗时/预算）与软停（无工具调用的最终回答）双轨；死循环用状态指纹检测；模型自称完成后须经独立校验。

- 单轮骨架：拼装提示与历史 → 模型生成 → 解析与参数校验 → 权限检查后执行 → Observation 回灌 → 终止检查。
- 硬性终止：最大轮数、token 与成本预算、耗时上限、并发配额；触发后进入收尾模式，让模型基于已有信息给降级答案而非裸抛错。
- 软性终止：模型输出不含工具调用视为完成，但需验收断言校验产物（跑测试、对账、字段齐全性或 Judge 评审），失败带原因回灌触发修复轮。
- 死循环检测：对工具名+归一化参数做状态指纹，连续重复即报警；处置依次为注入提醒、工具熔断、强制 Re-plan、终止。
- 工具报错要改写成模型可读的修复建议——看不懂失败原因是重复调用的头号诱因。
- 每轮记录结构化 Trace，供事后归因与回归测试。

## 进阶理解

### 终止条件体系：不止 max_turns

生产级 Harness 的终止条件是多维的：①轮数上限（默认如 20-30 轮，按任务分级）；②token 与成本预算（含输入累积，因为多轮循环中输入 token 每轮重复计费，是成本失控的主因）；③墙钟超时（保护上游 SLA）；④并发子任务配额（防止 fan-out 爆炸）。所有硬限触发都不应裸抛异常，而是进入『收尾模式』：向模型注入一条系统消息说明预算耗尽、要求基于现有证据给出带置信度标记的部分结论，让用户拿到可用的降级结果。

### 死循环与重复调用的检测

重复的本质是模型丢失了『这条路走过了』的记忆或陷入参数微调式震荡。检测：为每轮动作计算指纹 hash(tool_name + 规范化参数)，维护近 K 轮指纹集合；连续相同指纹、或滑动窗口内重复率超阈值即报警。分级处置：①注入反问消息（『你已连续 3 次调用 search 且参数相同，请改用其他工具或修正参数』），多数循环可在此解除；②工具级熔断：连续失败或重复的工具暂时下架；③升级为 Re-plan：清空近期轨迹、重新规划路径；④强制终止并降级。附带经验：循环高频诱因是工具返回错误信息不可读（模型看不懂失败原因只能重试），把工具报错改写成模型可理解的修复建议，比任何检测都便宜有效。

### 『模型说完成了』之后：验收闭环

模型的完成声明是主观判断，与任务客观完成之间存在三类缝隙：产物缺失（说要写文件但没写）、产物不达标（代码编译不过）、结论不实（引用了不存在的结果）。工程上把『完成』定义为一组可机检的验收断言，在循环之外执行：代码任务跑测试与静态检查，数据任务做行数/口径校验，生成任务做引用回溯与 Judge 评审。断言失败时把失败清单作为新一轮输入触发修复循环（有独立轮数预算），仍失败则输出降级结果并转人工。这一层是把 Agent 从『演示』推向『可托付』的分水岭。

**示例**：数据分析 Agent 执行『统计上月退款原因分布』，上游数据接口偶发返回空数组。

1. 第 1-2 轮：模型调用 query_refunds，返回空，Observation 回灌。
2. 第 3 轮：模型怀疑参数错误，以相同参数重试——指纹相同，计数器+1。
3. 第 4 轮：再次重试，触发重复检测，注入提醒消息；模型改为缩小日期范围查询成功，说明是全月数据量大导致超时截断为空。
4. 产出后验收：结果行数与订单总数对不平，校验失败回灌，模型补充处理了退款单状态过滤，二次验收通过，循环结束。

观察：没有指纹检测会空转烧 token，没有验收闭环会把口径错误的结果交付给业务方——两道防线缺一不可。
