# Q026 · Agent 长任务耗时从 5 分钟涨到 20 分钟，怎么排查延迟？不同业务场景下延迟和效果怎么取舍？

Agent 性能优化 · 中 · `延迟排查` `延迟效果取舍` `性能归因` `长任务`

> 真题来源：字节跳动 · Agent Harness · 一面（发帖人自述，未核实）

## 背景描述

延迟突增是线上 Agent 的典型事故题，考察『先定位再优化』的排查纪律，以及按业务场景做延迟-效果权衡的判断力。

## 引出的痛点

不看 Trace 就猜测『换小模型提速』，常常压错地方——延迟大头可能在某个慢工具或循环轮次暴涨，而不是模型本身。

## 考点

分段计时的延迟归因方法、常见延迟来源清单、按场景的延迟预算分级与取舍策略。

## 思考方向与解题思路

先给排查流程（Trace 分段定位），再列延迟来源与对策，最后按业务场景给取舍框架。

## 推荐答案

排查靠 Trace 分段计时归因：把端到端耗时拆到模型推理、工具执行、检索、排队各段，对比正常/异常样本找到突增段；常见根因是慢工具、循环轮次暴涨、输入变长导致推理变慢、限流排队。取舍按场景定延迟预算：交互式场景保首字延迟，批处理场景保吞吐与效果。

- 排查第一步：对比同任务新旧 Trace 的分段耗时（每轮模型调用、每个工具、检索、排队），定位突增段，不要先猜。
- 模型段变慢的常见原因：上下文变长（多轮累积输入 token）、模型/档位变更、推理服务负载高排队。
- 非模型段常见原因：某外部工具 P95 劣化、重试风暴、检索库变大未调索引、循环轮次从 N 涨到 3N。
- 修复对策：慢工具加超时+降级、上下文压缩控输入长度、并行化无依赖工具调用、缓存重复子问题的结果。
- 取舍框架：交互对话保首字延迟（可牺牲总耗时用流式）；批处理报告保最终质量（可牺牲耗时）；交易类硬 SLA 场景宁可降级回答也不超时。
- 权衡的本质：自主 Agent 用延迟和成本换任务效果是结构性代价，每个场景要明确买多少、能付多少。

## 进阶理解

### 分段归因：让数据先说话

正确姿势是先取同样任务的『之前 5 分钟』与『现在 20 分钟』各若干条 Trace，逐段对齐对比：每轮模型调用的输入 token 数与耗时、每个工具的执行耗时、检索耗时、请求排队耗时。四类典型结论：①输入 token 显著变长——历史未被压缩，推理随长度劣化且成本翻倍；②轮次暴涨——循环检测缺失导致反复探索；③某工具 P95 从 500ms 劣化到 8s——外部依赖故障，触发重试放大；④排队时间占比升高——推理服务容量不足或限流。四类对策完全不同（压缩/加循环防线/工具熔断降级/扩容或错峰），不定位就优化必然压错。

### 延迟-效果取舍的场景框架

Anthropic 对 agentic systems 的定性直接适用：这类系统经常以延迟和成本换取更好的任务表现——所以取舍不是要不要付，而是该场景付多少。分三档：①交互式（客服、编码助手）——用户等待预算秒级，保首字延迟（流式输出）与中间反馈（进度事件），复杂任务可以后台继续；②批处理（报告生成、离线任务）——无人等待，效果优先，允许多轮探索与更强模型，用吞吐和成本约束；③交易类硬 SLA（实时风控、交易辅助）——超时代价高于答错，预设降级路径：时间到就输出基于已有证据的部分结论。工程上把延迟预算写进 Agent Loop 的硬限（每工具超时、总耗时上限），让取舍成为配置而不是事故后的补救。

**示例**：数据分析 Agent 平均耗时从 5 分钟涨到 20 分钟，任务内容分布无变化。

1. 分段对比：模型段总耗时占比从 40% 降到 15%，工具段从 45% 升到 75%。
2. 下钻：新上线的取数工具 P95 从 1s 劣化到 6s，且失败重试率 30%，每次任务平均多跑 5 轮。
3. 处置：该工具加 3s 超时+降级到缓存数据，重试上限 1 次并回灌可读错误；耗时回落到 6 分钟。

观察：延迟排查的纪律与 bad case 归因相同——先 Trace 定位段，再谈优化手段；取舍则按场景预算明码标价。
