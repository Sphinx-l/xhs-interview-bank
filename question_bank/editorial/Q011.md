# Q011 · MCP（Model Context Protocol）的原理是什么？传输方式有哪些？它与 Function Calling 是什么关系、解决了什么问题？

Agent 工程化与运行环境 · 中 · `MCP` `Function Calling` `协议设计` `工具生态`

> 真题来源：面经帖自述信息不详（未核实）

## 背景描述

MCP 是 2025 年以来 Agent 岗的高频题，追问通常从原理一路打到『与 FC 的区别』『streamable 传输』『有什么坑』。

## 引出的痛点

只会说『MCP 是工具调用协议』而说不清 Host/Client/Server 三方结构与它相对 FC 的生态位，会被判定为只看过营销文。

## 考点

MCP 的三方架构与消息模型、stdio 与 Streamable HTTP 两种传输、MCP 与 FC 的层次关系（生态标准 vs 模型能力）。

## 思考方向与解题思路

先讲架构与协议（谁连谁、传什么），再讲传输与生命周期，最后厘清 MCP 与 FC 的关系和典型短板。

## 推荐答案

MCP 是开放协议，为 LLM 应用与外部能力提供标准化连接：Host 应用内嵌多个 Client，每个 Client 与一个 Server 一对一连接，Server 暴露工具/资源/提示词；通信基于 JSON-RPC 2.0，传输支持 stdio 与 Streamable HTTP；它与 FC 是配合关系——FC 管模型侧调用意图，MCP 管工具的发现与标准化接入。

- 三方架构：Host（承载 LLM 的应用）内运行多个 Client，各与一个 Server 1:1 连接；Server 提供 tools、resources、prompts 三类能力。
- 协议：JSON-RPC 2.0，消息分 request/result/error/notification 四类；initialize 握手协商版本与能力后进入消息交换。
- 传输两种：stdio 适合本地进程开销小；Streamable HTTP（POST + 可选 SSE 流式）适合远程，需 TLS 与鉴权。
- 与 FC 关系：FC 是模型生成结构化调用意图的能力，MCP 是工具发现与执行的生态标准，两者配合而非替代。
- 核心价值（工程视角通识）：把每个应用 × 每个工具的 M×N 集成降为 M+N——应用实现一次 Client、工具实现一次 Server 即可复用。
- 短板：工具描述质量参差、长连接与鉴权复杂、大量 Server 挂载时工具清单膨胀，需配工具检索与按需加载。

## 进阶理解

### 架构与消息模型

MCP 官方架构文档的核心表述：Host 是发起连接的 LLM 应用；Client 在 Host 内部与 Server 保持一对一连接；Server 向 Client 提供上下文、工具与提示词。消息基于 JSON-RPC 2.0，协议层负责消息组帧、请求-响应关联与错误码（标准 JSON-RPC 错误码 + 应用自定义区间）；初始化时 Client 发送 initialize 携带协议版本与能力，Server 应答自身版本与能力，Client 再发 initialized 通知后进入正常消息交换。这个设计使能力发现（capabilities 协商）成为协议内建行为，客户端可以按 Server 声明的能力选择性启用功能。

### 两种传输与工程取舍

stdio 传输用标准输入输出通信，适合本地子进程场景——进程管理简单、同机通信高效，是本地工具（文件系统、本地 CLI 封装）的默认选择。Streamable HTTP 用 HTTP 承载消息，客户端到服务端走 HTTP POST，服务端可用 SSE 做流式返回；远程场景需考虑 TLS、来源校验、认证授权与速率限制。工程要点：本地优先 stdio，跨网络/多客户端共享才上 Streamable HTTP；长任务用 progress token 上报进度；错误要回传结构化错误信息而非静默失败，否则上层 Agent 无法自我修复。

### MCP、FC 与工具生态的层次

在 MCP 出现前，接入一个工具意味着：为每个模型 API 写一遍工具定义（FC schema），为每个应用写一遍执行逻辑——这是工程视角下的 M×N 重复劳动（通识性结论，非协议文档原文）。FC 定义了模型输出 tool_call 的格式（这是模型能力，各厂商 API 自有协议）；MCP 定义了工具的发现（list_tools）、描述（JSON Schema）与调用（call_tool）的标准通道。因此『没有 MCP 之前怎么调工具』的答案是：应用自己维护工具清单与 Schema、自己写执行胶水代码，换模型/换应用都要重做。有了 MCP，工具方实现一次 Server 即可被所有兼容 Host 使用。A2A 则再往上一层解决 Agent 之间的互操作，Skill 是『把流程说明+资源打包成可挂载能力』的封装形态，与 MCP 的工具层互补。

**示例**：IDE 内的编程助手需要数据库查询、文件检索、工单系统三类能力。

1. 无 MCP：IDE 助手为三类能力各写集成代码并维护工具 Schema；换一个助手全部重写。
2. 有 MCP：三个能力方各发布一个 MCP Server；IDE 作为 Host 内嵌三个 Client 分别连接（本地工具走 stdio，工单系统走 Streamable HTTP + OAuth）；助手通过 list_tools 动态获得工具清单，模型用 FC 生成调用，Client 经协议转发到对应 Server 执行并回传结果。

观察：集成成本从 M×N 降为 M+N，且工具清单可动态发现——这就是 MCP 相对私有胶水代码的结构性收益。
