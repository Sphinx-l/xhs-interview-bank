# Q002 · ReAct 范式的工作流程是怎样的？工程实现中消息格式如何设计，tool_response 用什么角色传回？

AI Agent 架构设计 · 中 · `ReAct` `消息格式` `工具调用` `Thought-Action-Observation`

> 真题来源：面经帖自述信息不详（未核实）

## 背景描述

ReAct 是 Agent 面试的基础必考题，但多数候选人只会背 Thought→Action→Observation，面试官往往追问到消息序列与角色设计的工程细节。

## 引出的痛点

不掌握消息格式细节就无法真正实现 ReAct：tool_response 的角色选择错误会导致多轮后模型混淆自己与工具的边界。

## 考点

ReAct 的循环机制、消息序列的工程表示、tool_response 的角色选择及原因。

## 思考方向与解题思路

先讲清循环与消息序列的对应关系，再给出具体的 messages 数组结构，最后解释角色设计的原因和两种主流实现方式的取舍。

## 推荐答案

ReAct 让模型以交错生成推理轨迹（Thought）与任务动作（Action），并把动作结果作为观察（Observation）回灌上下文继续推理，循环直到得出答案；工程实现上每轮迭代是消息数组追加，工具结果用独立的 tool 角色传回。

- 循环结构：Thought（分析现状）→ Action（产出工具调用）→ Observation（工具执行结果回灌）→ 下一轮 Thought，直到模型给出无工具调用的最终回答。
- 消息序列：user 问题 → assistant（含 Thought + tool_call）→ tool（工具结果）→ assistant（下一轮推理）→ …… → assistant 最终回答；ReAct 论文的原始形式是用纯文本 Thought/Action/Observation 标记实现同一结构。
- tool_response 应使用专用的 tool 角色（OpenAI 协议中的 tool 消息）传回，而不是伪装成 user 或 assistant：专用角色让模型能明确区分『我说过的』和『环境告诉我的』，多轮后不易混淆来源。
- 原生 Function Calling 由 API 强约束工具调用格式，解析稳定；文本协议（在 Prompt 中约定 Thought/Action 格式自行解析）兼容不支持 FC 的模型，但格式错误率更高。
- 工程要点：tool_call_id 必须与请求一一对应、工具异常也要作为 Observation 回灌而非静默吞掉、每轮控制消息总量防止上下文膨胀。

## 进阶理解

### ReAct 循环与消息序列的对应

ReAct（Yao et al., 2022）的核心是把推理（reasoning traces）与行动（task-specific actions）交错生成：推理轨迹帮助模型归纳、跟踪和更新行动计划并处理异常，行动让模型对接外部知识源与环境获取信息。映射到消息数组：每一轮迭代 append 一条带 tool_call 的 assistant 消息和一条（或多条）tool 结果消息；模型看到 Observation 后决定下一轮是继续调工具还是给出最终答案。终止条件是模型输出的 assistant 消息不含任何 tool_call，或触发外部限制（最大轮数、token 预算）。

### 为什么 tool_response 必须有独立角色

工具结果本质上是『环境的发言』，既不是用户说的，也不是模型说的。用 user 角色伪装工具结果，模型容易把 Observation 当作用户新指令，出现被工具输出注入（间接提示注入）的风险；用 assistant 伪装则会让模型把环境反馈当成自己的历史结论，重复推理时倾向维持错误。OpenAI 的 Chat Completions 协议为此定义了 role=tool 的消息，必须携带 tool_call_id 与对应的 tool_call 匹配；Anthropic 的 Messages API 用 tool_result 内容块放在下一条 user 消息中，同样是显式标记。两种协议殊途同归：结构上可区分来源、可审计。

### 原生 Function Calling 与文本协议的取舍

原生 FC：在请求中声明 tools（JSON Schema），模型返回结构化 tool_call 字段，框架解析后执行、把结果以 tool 角色回灌。优点是格式可靠、支持并行工具调用；缺点是依赖模型/协议支持，Thought 过程可能被隐藏。文本协议（ReAct 原始形态）：在 System Prompt 中约定输出格式（如 Thought: ... \n Action: tool_name[args]），框架用正则/解析器抽取。优点是任何模型都能跑、Thought 完全显式；缺点是解析脆弱，需要处理格式不合法的重试。生产上优先原生 FC，文本协议用于不支持 FC 的模型或需要完全显式推理轨迹的场景。

**示例**：用户问『2026 年图灵奖得主是哪国人』，模型知识截止不知道。

1. user: 问该问题。
2. assistant（Thought：我不知道，需要搜索 → tool_call: search(query="2026 图灵奖得主")）。
3. tool（tool_call_id 对应，返回摘要：得主为某科学家及其国籍）。
4. assistant（Thought：拿到结果，可以直接回答 → 无 tool_call 的最终回答）。

观察：推理与行动交替，使模型能用环境事实纠正自身知识盲区，这正是 ReAct 相对纯思维链降低幻觉与错误传播的关键。
