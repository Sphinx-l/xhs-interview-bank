# Q029 · 用户中途取消任务、或版本热更新时正在运行的 Agent 怎么处理？

Agent 性能优化 · 中 · `任务取消` `热更新` `检查点` `优雅终止`

> 真题来源：字节跳动 · Agent Harness · 一面（发帖人自述，未核实）

## 背景描述

取消与热更新考察的是 Agent 运行时的生命周期管理，追问常到『取消到一半的工具调用算不算执行』与『旧版本任务跑不跑完』。

## 引出的痛点

没有协作式取消机制，强制杀进程会留下半成品副作用（发了一半的消息、写了一半的文件）；热更新不打版本标记则新旧任务混杂无法排查。

## 考点

协作式取消（检查点退出+副作用安全）、任务级版本绑定、热更新的灰度与在途任务策略。

## 思考方向与解题思路

先讲取消的信号传递与安全退出，再讲热更新的版本策略，两者共用检查点与状态落盘机制。

## 推荐答案

取消用协作式机制：取消信号传给执行循环，在安全检查点（工具调用之间）退出，已完成副作用按幂等记录、半成品不清理错杀；热更新采用任务级版本绑定——在途任务带旧版本跑完或迁移到检查点后重入，新请求走新版本，配合灰度与回滚。

- 协作式取消：循环每轮开始检查取消标志（或监听取消通道），收到后在工具调用之间的安全点退出并落状态，而不是直接杀线程。
- 副作用安全：已执行的工具调用记录在案（幂等键、结果），取消后可向用户展示已完成部分；进行中的调用等待其完成或超时，不留悬挂副作用。
- 取消的原因区分：用户主动停（保留已产出）、超时强停（降级输出）、错误中止（记录现场）——三种的收尾动作不同。
- 热更新策略：任务发起时绑定版本号（模型/提示/工具集），在途任务默认用原版本跑完；长任务可选『检查点迁移』——在新版本兼容状态下从最近检查点重入。
- 灰度与回滚：新版本小流量放量，行为回归通过后全量；版本号打到每个 Trace span，出问题可按版本切片定位与回滚。
- 框架支撑：图编排引擎普遍提供持久化检查点与中断/恢复机制（如 LangGraph 的 checkpointer 与 interrupt/resume），是实现优雅取消与重入的现成基础设施。

## 进阶理解

### 取消：信号、检查点与副作用

取消的正确实现是协作式（cooperative）而非抢占式：请求层接收取消指令后向执行器发取消信号（设置标志/关闭 channel/任务取消 API），Agent Loop 在每轮边界检查信号，在两次工具调用之间的安全点退出。安全点的定义：没有进行中的外部副作用。已在执行的工具调用要么等待完成要么按其自身超时处理，因为中途掐断外部请求不代表服务端没执行（支付类尤其危险，参见幂等与先查后试原则）。退出时落盘：已完成步骤清单、中间产物、终止原因（用户取消），前端展示部分结果而非一切归零。区分三类终止：用户取消（保留产出、可续跑）、系统超时/预算强停（进入收尾模式给降级结论）、错误中止（保留现场供排查）——三者收尾语义不同，不能一个 kill 了之。

### 热更新：版本绑定与在途任务

热更新的核心矛盾：部署是瞬时的，任务是长时的。策略分层：①任务级版本绑定——任务创建时固化所用模型/提示/工具集版本，在途任务用旧版本跑完，保证单个任务内部行为一致、Trace 可解释；②检查点迁移——对超长任务，若新旧版本状态结构兼容，可在检查点处用新版本重入继续执行（LangGraph 这类引擎的 checkpointer 与 interrupt/resume 即为此设计，还支持时间旅行回放到任意检查点）；③灰度放量——新版本先小流量，跑行为回归集与线上切片对比，无退化再全量；④可回滚——版本号打进每个 span，出问题时按版本定位影响面，配置回滚旧版本。变更管理上，提示词、工具 Schema 与模型都视为需要回归与灰度的『代码』，而不是随手可改的配置。

**示例**：报告生成 Agent 跑到 70% 时用户点了停止；同晚平台发布新版提示词。

1. 取消：前端发取消请求，循环在当前工具返回后的检查点退出；已完成的三个章节与中间数据落盘，状态标记 user_cancelled，用户可稍后续跑。
2. 热更新：该任务版本绑定旧提示词继续在途逻辑不受影响；新发起的任务走新版本并打新版本号。
3. 验证：新版本先灰度 10% 流量跑回归对比，Trace 按版本切片无退化后全量。

观察：取消与热更新的共同底座是检查点与版本绑定——把长任务变成可暂停、可解释、可迁移的有状态对象。
