# Q003 · ReAct 与 Plan-Execute 两种范式有什么区别？分别适合什么任务？为什么简单任务不该先做完整 Plan？

AI Agent 架构设计 · 中 · `ReAct` `Plan-Execute` `任务规划` `范式选型`

> 真题来源：字节跳动 · Agent Harness · 一面 · 同题另见 3 处（发帖人自述，未核实）

## 背景描述

『你们 Agent 用的 ReAct 还是 Plan-and-Execute』是高频开场题，追问方向通常是两类范式的失败模式与混合使用。

## 引出的痛点

死守单一范式会在另一类任务上翻车：长链路任务用 ReAct 容易中途漂移，简单任务用 Plan-Execute 白付规划成本。

## 考点

控制流归属差异、各自适用任务特征、规划开销与稳定性的权衡、混合路由方案。

## 思考方向与解题思路

先对比两种范式的控制结构，再给出任务特征到范式的匹配表，最后说明生产系统常见的『路由 + 混合』做法。

## 推荐答案

ReAct 每一步都由模型即时决策、走一步看一步，灵活但长任务易漂移；Plan-Execute 先生成完整计划再逐步执行，全局性好但计划质量依赖规划器且响应慢，适合步骤多、依赖关系复杂的任务；生产上常按任务复杂度路由，简单任务直连 ReAct。

- 控制流差异：ReAct 的决策粒度是单步（每轮根据最新观察决定下一步）；Plan-Execute 把决策前置为一次性计划（Planner 产出子任务列表），Executor 按计划执行，必要时 Re-plan。
- ReAct 适合：步数少（一般 3-5 步内）、路径不确定、需要边探索边调整的任务，如单点查询、信息核实、简单客服工单。
- Plan-Execute 适合：步数多、子任务间有依赖与并行关系、需要进度可追踪与断点恢复的任务，如多源报告生成、批量代码改造、多 Agent 协作编排。
- 简单任务先做完整 Plan 的代价：多一次 LLM 调用增加首响延迟与成本，且 Planner 可能对简单任务过度拆分（过度规划），反而引入执行偏差。
- 失败模式：ReAct 长任务中途目标漂移、陷入循环；Plan-Execute 计划一步错步步错，需要重规划机制兜底。
- 生产方案：入口按复杂度路由（简单 query 直接 ReAct，复杂 query 走 Plan-Execute），执行中允许 Executor 上报异常触发局部 Re-plan。

## 进阶理解

### 两种范式的结构对比

ReAct 是『感知-决策-行动』的滚动式控制：每轮只决定下一个动作，计划隐含在推理轨迹中，优点是对环境变化自适应强，缺点是没有全局视图，长任务（十几步以上）容易遗忘初始目标或重复探索。Plan-Execute 把任务求解拆成 Planner 与 Executor 两个角色：Planner 一次生成结构化计划（子任务列表、依赖图、可并行的分支），Executor 逐项执行并把状态写回计划看板，偏差超阈值时触发 Re-plan。这本质是用『显式计划』换『全局一致性』，代价是规划延迟和计划本身的可靠性风险。

### 按任务特征选型

判断维度：①步数与深度——浅任务 ReAct 足够，深任务需要计划防止漂移；②子任务依赖——有 DAG 依赖（先取数再分析再成文）时计划可显式表达并行与顺序，ReAct 串行浪费并行机会；③可逆性——动作不可逆（发送、支付）时应先计划并经确认再执行；④延迟预算——交互式场景难以承受先规划的额外一跳。据此可以得出工程路由规则：用轻量分类器或模型自评（任务需要几步、是否可并行）把 query 分到 ReAct 快路径或 Plan-Execute 慢路径。

### 为什么不能所有任务都过 Planner

假设 Planner 准确率有限，把简单任务（一问一查一答）也送入规划，等价于给高流量路径叠加一个错误源和一次额外时延：规划过度拆分会放大执行噪声，拆出的伪依赖会串行化本可省略的步骤。面试常见追问『简单任务为什么不能直接用 ReAct 完成』考察的正是这层成本意识——Planner 是为复杂度买的保险，简单任务没有可保的风险。

**示例**：知识问答机器人同时收到两类问题。

1. 『公司年假政策是什么』：单跳检索可答，路由到 ReAct，一次检索两轮内返回。
2. 『对比过去三年三个业务线的营收并生成分析报告』：多源取数、口径对齐、先算后写，路由到 Plan-Execute：Planner 拆出 6 个带依赖的子任务，两个取数任务并行执行，全部完成后进入成文阶段。

观察：同一系统内按复杂度分流，比统一用单一范式在延迟、成本、稳定性三个维度都更优。
