# Q010 · 上下文预算有限时，系统提示、工具 Schema、记忆、轨迹与中间结果如何做全局分配？如何量化压缩损失？

AI Agent 架构设计 · 高 · `上下文工程` `预算分配` `压缩损失` `上下文管理`

> 真题来源：阿里巴巴 · 大模型 Agent · 三面 · 同题另见 1 处（发帖人自述，未核实）

## 背景描述

这是面向资深候选人的系统性设计题：不再问单个压缩技巧，而是把上下文当作稀缺资源做全局最优化分配。

## 引出的痛点

各模块各自为战地往上下文里塞内容（Prompt 工程师加指令、工具团队加 Schema、记忆团队加召回），预算很快耗尽且无人对整体效果负责。

## 考点

上下文分区与预算表、按边际收益分配的方法、压缩损失的量化手段、动态调整机制。

## 思考方向与解题思路

先建立『预算表 + 分区』的全局视角，再讲分配原则与量化，最后给出动态重分配的工程闭环。

## 推荐答案

把上下文建模为带预算表的分区资源：硬约束常驻高优先，工具 Schema 按需加载，记忆限条注入，轨迹滚动压缩、大产物外置；分配以单位 token 的边际收益为准，压缩损失用回归集任务完成率与关键信息命中率量化。

- 预算表分区：系统提示/约束、工具 Schema、记忆、轨迹、中间产物、输出预留各设配额（如 10%/15%/10%/35%/20%/10%），按任务类型调档。
- 分配原则：常驻区最小化；低频工具两级加载（目录先筛再展开 Schema）；记忆按置信度限条注入；产物优先外置留句柄。
- 工具治理：上百工具全量注入既占预算又降低选择准确率；目录/检索筛出候选子集再展开是标准解法。
- 轨迹管理：只完整保留最近 K 轮，早期压成结构化摘要（目标/决策/状态），重复失败调用折叠为一行。
- 损失量化：探针问题命中率、回归集任务完成率、约束违反率三层指标；超阈值调高该类信息保留等级。
- 动态重分配：按阶段切换预算档（规划/执行/成文）；超支降级顺序为先轨迹、再工具、最后记忆，硬约束永不裁。

## 进阶理解

### 全局视角：上下文是分区资源

成熟做法是把上下文工程当成资源调度问题：每个消费者（指令、工具、记忆、轨迹、产物）申报需求，调度器按任务阶段与边际收益分配 token 预算。三个设计支点：①常驻区最小化——只有身份、硬约束、输出规范等不可再生信息常驻；②按需进入——工具 Schema、长尾记忆、历史产物都要经过『准入』（目录索引、检索、句柄引用）而非默认在场；③出口分级——压缩、折叠、外置三档出口，分别对应有损保义、降采样、无损移出。这个框架下，压缩不再是孤立技巧，而是预算超支时的调度动作。

### 量化压缩损失：从省 token 到保效果

压缩的代价必须可度量。三层度量：①信息层——对被压缩内容构造探针问题（关键约束、数字、决策），压缩后上下文能否答出，算命中率；②任务层——长任务回归集上跑压缩前后对比，看任务完成率与约束违反率的变化；③成本层——压缩本身消耗的 token 与延迟是否低于收益。把三类指标做成 dashboard，每次调整分区配额都跑回归，才能避免『修好一类 case 压坏另一类』。探针集的构建可以从线上 trace 挖掘：高频引用的早期信息就是最不能丢的信息，优先升保留等级。

### 动态预算与工程闭环

静态配额只是起点，运行时需要：①阶段感知——Plan 阶段放大轨迹与目标区，工具执行阶段放大产物区，生成阶段收缩工具区；②超支处理——预算耗尽时的降级顺序应为先压轨迹、再裁工具 Schema、最后压记忆注入，硬约束永不裁；③估算器——精确的 token 计数（含消息结构开销）提前预判溢出，而不是等 API 报错；④观测——记录每轮上下文构成快照，事后可复盘哪一区挤占了预算导致效果下降。能说出『配额表 + 边际收益 + 损失量化 + 动态降级』四件套，就构成了完整的上下文工程答案。

**示例**：128K 窗口的 Coding Agent，工具 80 个，任务进行到第 25 轮，预算告急。

1. 盘点：System 8K、工具 Schema 30K（全量）、记忆 6K、轨迹 40K、产物引用 15K、已用 99K，输出需预留 20K。
2. 调度：工具 Schema 改两级加载只展开当前相关 12 个（省 24K）；早期轨迹压成结构化摘要（省 18K）；两个大文件外置留句柄（省 10K）。
3. 校验：对被压缩轨迹跑探针问题（早期确定的接口契约），命中 9/10；未命中的 1 条（版本号约束）升保留等级回灌。
4. 结果：总占用降到 66K，任务继续且后续生成未再溢出。

观察：预算表让『该裁谁』变成显式决策，探针与回归让『裁得起吗』变成可验证问题——这就是上下文工程与随手压缩的分界。
