## 来自 02.webp

一、多阶段RAG，BM25 加向量混合检索——两种结果怎么合并的？实际提升在哪？

用 RRF（倒数排名融合）把两路结果按排名加权合并，不是直接加分数。

两路各自排 Top N，每篇文档的 RRF 分数是 1 除以（排名加 k），k 取 60，两路分数加和排序。BM25 抓关键词（错误码、API 名），向量抓语义（同义词、换说法），互补。

提升在两个环节：召回率比单路高 10%-15%，口语化提问尤其明显；上下文更全，幻觉减少。

二、PDF 扫描件、OCR、表格结构化这些，踩过坑没？

扫描件质量和表格结构是两个大坑，一个翻车后面 RAG 全白做。

扫描件：模糊、倾斜、阴影、水印，OCR 识别率直接腰斩。中英文混排容易被拆成单字母或阅读顺序搞反。双栏排版按行读会串行。

表格：合并单元格最头疼，解析工具常把一个合并格拆成多个空格。嵌套表格 Unstructured 和 Camelot 都处理不好。无边框表格根本识别不出是表格，字段全乱。

三、识别准确率能做到多少？

看文档质量，不是一个固定数字。

清晰印刷体 PDF 的 OCR 准确率在 95% 到 99% 之间，基本不用人工校对。扫描件看质量，80% 到 95%，模糊、歪斜的能掉到 70% 以下。手写体最差，70% 到 85%，而且还看字迹。表格结构还原是另一回事——简单表格 90% 以上，带合并单元格的复杂表格可能只有 70% 到 80%。

实际项目里我会对识别结果做后处理：用正则校验关键字段格式，置信度低的片段标出来供人工复核。

## 来自 03.webp

四、State 和 Checkpoint 怎么搞的？多个 agent 一块跑，状态不会互相覆盖吗？

LangGraph 基于 Pregel BSP 模型，同一 super-step 内可以并行跑多个节点，不会互相覆盖是因为所有节点读同一份 state 快照，更新先缓存，super-step 结束时靠 reducer 合并写入。

Checkpoint 用 SqliteSaver 或 PostgresSaver 持久化，每个 super-step 后自动存快照，出错了回滚到上一个检查点。

同一 thread 下节点不是强制串行的——add_parallel 可以显式并行。节点不直接原地改 state，只返回增量更新，字段 reducer 控制合并策略，避免数据覆盖。不同 thread_id 之间 state 天然隔离，各自独立会话。

五、State 全局管理怎么做的？

定义一个 TypedDict 作为全局 state schema，所有节点共享，各自写自己负责的字段。

每个节点函数接收完整 state，返回一个 dict 作为增量更新，框架自动合并到全局 state。

多 Agent 场景下，不同 Agent 通过 key 前缀或命名空间隔离各自的字段，比如搜索 Agent 只写 search_results，代码 Agent 只写 code_output。

实际写代码时要注意：state 的 key 要提前规划好，节点之间通过 state 传数据而不是通过函数参数，这样图的结构才清晰。

## 来自 04.webp

六、Choice 接口包成 MCP 工具，标准接口怎么设计？兼容性有问题吗？

MCP 工具定义三要素：name、description、inputSchema，标准化就在这里。

name 是工具唯一标识，description 写清楚工具干什么、什么时候该调用，inputSchema 用 JSON Schema 定义每个参数的类型、是否必填、默认值。

兼容性问题的关键是不同大模型厂商的 function call 格式不一致。OpenAI 用 tools 数组加 tool_choice 字段，Anthropic 用 tool_use 块。包成 MCP 之后，服务端只暴露 MCP 协议的 tools/list 和 tools/call 接口，客户端负责把 MCP 工具描述翻译成各模型原生格式。这样换模型不需要改服务端代码，兼容性问题丢给了 MCP 客户端。

实际项目中遇到过一个坑：某些模型对 JSON Schema 里嵌套对象的支持不好，需要把复杂参数拍平成一维。

七、现场举一个你项目里的 MCP 工具例子，入参出参怎么定义的

拿"订单查询"工具举例。

入参：order_id（字符串，必填，订单号）、fields（字符串数组，可选，指定返回哪些字段，比如只查状态不查商品明细）。

出参：一个 JSON 对象，包含 order_status、amount、created_at、items 列表等字段。

不管底层是调数据库还是调 HTTP 接口，对外就一个统一的 JSON 返回结构。

inputSchema 的 JSON Schema 大概是：type 为 object，properties 里定义 order_id 和 fields 各自的类型和描述，required 数组里放 order_id。MCP 客户端拿到这个 schema 后，自动生成发给大模型的工具描述。

## 来自 05.webp

八、没有 MCP 之前，大模型调工具是怎么个流程？

模型输出 function call JSON → 业务代码解析 → 调函数 → 结果拼回 prompt → 再调模型。

核心痛点：每家厂商的 function call 格式不一样。OpenAI 是 tool_calls 数组，Anthropic 是 content block 里的 tool_use 类型。每次换模型，解析代码和拼结果的逻辑全部要改。MCP 把这个流程统一了，工具定义和调用协议跟模型无关。

九、MCP 有什么坑或者短板？

部署复杂、传输受限、认证不统一、流式弱、Token 消耗大。

部署：每个 MCP server 独立进程，端口冲突、进程管理都是运维成本。传输：stdio 只能本地用，远程切 SSE 但它是单向推送。认证：协议没规定统一认证，各 server 自己搞 token 或 OAuth。流式：工具结果必须全量返回，不能 token by token 流式输出。

Token：tools/list 返回全量工具描述，工具多了每次请求都带完整列表，吃上下文窗口。

十、MCP 返回结果能不能流式？

基础 stdio 传输下工具结果需完整返回，新版 Streamable HTTP 可以推送进度通知，但工具最终返回的 content 仍是完整 JSON，不像大模型那样逐 token 流式输出。

Streamable HTTP 模式下，tools/call 过程可以推送进度事件和日志给客户端，用户不用干等。但工具的业务结果本身不支持分片流式返回，这跟大模型的 token 流式是两回事。

## 来自 06.webp

十一、你项目是多 Agent 主子架构吗？

是的，主管分派模式，一个 Supervisor 管调度，下面几个专职 Agent 各管一摊。

| 角色 | 干什么 |
| --- | --- |
| 主管 Agent | 拆解用户任务、分派给对应的专职 Agent、检查结果、不满意打回重做 |
| 搜索 Agent | 负责 RAG 检索和联网查资料 |
| 代码 Agent | 负责写代码、跑沙箱、调试 |
| 分析 Agent | 负责数据分析和报告生成 |

我项目里约束同级 Agent 不直接通信，所有交互通过 Supervisor 中转，方便管控和审计。架构上 LangGraph 本身也支持对等 Agent 点对点通信（Network 模式），只是可控性不如中心化调度。

十二、一次会话 token 大概多少？有没有爆过上下文窗口？

常规对话 15K 到 30K token，多轮工具调用能到 40K 到 50K。

复杂任务带 RAG 检索和多步推理的时候，上下文增长很快——检索回来的文档片段、工具执行结果、多轮对话历史，加起来轻松到几万 token。

目前用的 Qwen2.5-72B 上下文窗口 128K，还没爆过。但也在做预防：超过 30 轮对话做摘要压缩，RAG 检索结果做重排序只保留最相关的 Top 3，减少无效内容占位。

十三、用的什么模型？Qwen 是吧，哪个版本？

Qwen2.5-72B-Instruct，通过阿里云 API 调。

选这个版本是因为推理能力在同等规模里表现不错，尤其是中文场景和工具调用。72B 参数在成本和效果之间平衡得比较好，不用上到几百 B 的大模型。长上下文窗口 128K，多轮 Agent 对话不会轻易超限。

## 来自 07.webp

十四、子任务挂了，比如数据抓回来空的，工作流怎么重试或降级？

LangGraph 的条件边实现失败路由，重试靠循环边，降级靠 fallback 节点。

节点执行完后检查返回状态。正常走 next 边，失败了走 retry 边。retry 边指回自己，带一个重试计数器。重试策略是指数退避，最多重试 3 次。超过上限走降级边，指向一个 fallback 节点。

降级逻辑分三档：有缓存优先读缓存返回，没缓存给一个预设的默认值或兜底回复，关键业务任务转人工审核队列，同时告警通知。

整个流程编在图里，不是散落在代码各处的 if-else，排查问题时一眼就能看到每个节点的成功和失败路径。

十五、FastAPI 加 SSE 做流式，LangGraph 图状态机里怎么抓到每个节点的结果实时推前端？

用 LangGraph 的 astream_events 接口捕获节点事件，FastAPI 通过 SSE 推到前端。

astream_events 遍历图执行过程中每个节点开始和结束的事件，过滤出 on_chain_start、on_chain_end、on_tool_start、on_tool_end 这几类关键事件。每个事件包含节点名称、当前状态、输出数据。

FastAPI 这端把事件流通过 asyncio 队列转成 SSE 格式，前端 EventSource 接收后实时更新 UI——比如展示"正在检索知识库""正在生成回复"这些进度提示。

需要注意 astream_events 默认是 streaming 模式，某些节点内部的中间结果也会暴露出来，要做一层过滤避免前端收到太多噪音。

## 来自 08.webp

十六、为什么选 LangGraph 不直接用 LangChain？

LangChain 是线性的链，Agent 工作流是循环的图，需求不匹配。

| 特性 | LangChain | LangGraph |
|------|-----------|-----------|
| 编排方式 | Chain 链式，A→B→C 定死 | 有向图，节点加边，循环和分支都行 |
| 流程控制 | 线性执行，做条件分支很费劲 | 条件边按函数返回值路由，天然支持循环 |
| 状态管理 | 链间手动传参 | 内置共享 state，每步自动读写 |
| 检查点 | 没有 | 每步自动存快照，支持回滚和重放 |

Agent 的实际工作流是环形的——调工具、看结果、不够继续调、够了才输出。
LangChain 的 Chain 做不了这个循环，LangGraph 的条件边和循环边天然支持。
