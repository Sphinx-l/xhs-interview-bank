3.项目一，项目中的元素定位 Agent是什么，用途解释一下

元素定位是指找到页面上想要操作的那个 UI 组件（比如"登录按钮"、"用户名输入框"、"购物车图标"）。它一个具备智能理解能力的组件，不再使用固定的选择器，而是：理解意图，观察当前页面，推理决策，动态输出定位方式。在项目中，我把当前页面的 DOM 结构简化一下，提取出所有可交互元素（按钮、输入框这些），连同它们的文本、角色、属性一起传给 LLM。同时我会告诉 LLM 用户想点的是“登录按钮”。LLM 会分析页面上哪个元素最符合这个描述，然后返回一个定位策略，比如“用文本‘登录’去找”或者“用 role='button'去找”。执行层再根据这个策略去实际操作。用途主要是两个：一是让自动化测试脚本更鲁棒，前端小改动不会导致大规模脚本维护；二是支持自然语言驱动的测试，非技术人员也能写用例，因为 Agent 会自己去理解“登录按钮”指的是哪个元素。

了解动态容错吗？

项目中涉及了简单的容错机制，动态容错是让智能体在真实、不确定环境中保持鲁棒性的核心能力，包含三个关键环节：

01 实时感知与检测。Agent需要能通过多维度的监控，比如传感器信号、任务执行状态、外部反馈等，快速发现异常。这种检测不依赖于预设的阈值，而是结合当前上下文判断是否偏离预期。

02 动态决策与调整。与传统静态冗余不同，动态容错会根据故障类型和剩余能力，自主选择策略。比如是切换备用模块、在线重新规划路径，还是执行安全降级、保留核心功能。这通常需要结合强化学习或基于模型的推理。

03 学习与演进。好的机制不仅应对当前故障，还能把这次经验更新到知识库中，提升未来对类似问题的预判和处理效率。

Summary 节点在Agent项目或者整个报告生成的链路中，作用是什么？

Summary 节点的首要作用是认知降维。它将多个子任务返回的、可能存在冗余甚至矛盾的原始数据，提炼成结构化的核心论据，避免后续节点发生‘上下文爆炸’。其次，它解决了多源异构数据的对齐问题。无论上游调用的是代码解释器、搜索引擎还是数据库，Summary 都能将其封装成下游决策节点可直接理解的统一语言。而在在长链路任务中，Summary 扮演了工作记忆的角色。它把已经完成的计算步骤‘封存’为一段精炼的事实陈述，从而释放 Agent 的短期记忆负载，去处理下一阶段的新任务。

8.你怎么理解MCP，Prompt，CLI，Skill，Harness这些概念，以及他们之间的关系？

MCP是 Model Context Protocol 的缩写，本质是一个协议标准，定义了 Agent 或 LLM 如何与外部工具、数据源进行交互。他统一了工具调用的格式、鉴权、生命周期管理。它作用把各种不同的工具（本地文件、数据库、API、浏览器等）抽象成一套标准化的接口，这样 Agent 不需要为每个工具写定制的调用逻辑。

## 来自 07.webp

Skill我个人理解它是更高层的封装。一个 Skill 往往包含多个步骤、多个工具调用的组合，甚至包含一些 prompt 模板和业务逻辑。比如“发送邮件”是一个工具（通过 MCP 暴露），但“撰写一封得体的会议纪要邮件并发送”就是一个 Skill，它可能包含：调用 LLM 生成内容 → 调用邮件工具发送 → 调用日历工具更新状态。Skill 是面向任务的、可复用的能力单元。

Prompt是直接输入给 LLM 的文本指令。但它和前面的概念会交叉：一个 Skill 内部会包含多个 Prompt，比如规划用的 Prompt、工具选择用的 Prompt、结果总结用的 Prompt。Skill 本质上就是"Prompt + 工具调用编排 + 控制逻辑”的组合。

CLI 是指 Command Line Interface。在 Agent 系统中，CLI 可以有两个角色：一是 Agent 可以去调用的命令行工具，这时它算是一种特殊的 Tool；二是 Agent 系统本身的交互入口，比如通过命令行启动一个 Agent 会话。我更倾向于从 Tool 的角度去理解它——CLI 是暴露给 Agent 的一种

Harness，我理解它是Agent 的框架环境。比如你写好了一个 Agent，它包含各种 Skills、Prompt、Tool 配置，但你需要在一种可控的环境里去跑它、评估它的表现、调试它的行为。在Agent场景里，Harness可以批量运行Agent并收集执行轨迹，用内置或自定义的指标做自动化打分，也可以接入LLM-as-Judge做更灵活的定性评估。它能帮助开发者系统化地做回归测试和A/B对比，在迭代Agent时快速判断新版本有没有退化。

它们的关系是：Harness 评测 Agent，Agent 调用 Skill，Skill 通过 MCP 调用 CLI 等底层工具，Prompt 贯穿全程。

02　超时与异常处理：候选人可能长时间不说话或者答非所问。我会设置超时机制，超时后追问决策Agent给出提示或主动换题。另外对明显无效的回答，要限制追问次数，避免死循环。

11.你这个产品，怎么避免每一步出现重新规划，导致路径震荡？

路径震荡的本质是：Agent在每一步都基于当前的、局部的上下文重新做全局规划，导致上一轮的决定被下一轮推翻，来回摇摆，既消耗Token又难以收敛。从四个层面来解决这个问题。

分层规划。将规划拆解为顶层计划和底层执行两个

## 来自 11.webp

层次。顶层计划在任务开始时生成，包含粗粒度的步骤序列，并在没有遇到重大障碍前保持冻结。底层执行只负责当前步骤内的工具调用和参数调整，不推翻顶层计划。只有当某一步持续失败，或返回信息与顶层假设严重冲突时，才触发有条件的重新规划。

决策记忆与约束。路径振荡往往是因为Agent忘记了之前为什么做某个决定。我会在状态中显式记录上一次决策的理由，以及已经尝试过并失败的路径。这些记录作为硬约束输入到下一次规划中，防止Agent反复在几条路径之间来回切换。

惯性机制与阈值控制。引入置信度变化阈值，只有新信息对当前计划的置信度影响超过预设阈值时，才允许重规划。同时设置步数窗口，强制规定在生成计划后的K步内禁止重新规划，因为许多看似矛盾的信息在执行几步后会自动消解。

状态机化。将Agent的执行过程建模为有限状态机，规划、执行、评估、重规划是明确分离的状态。只有在评估状态中判定“当前计划不可继续”时，才转移回规划状态。这种严格的状态转移约
