## 正文题面

- Round 1：BQ
- 主要问了两个问题：一次简化复杂系统的经历；当用户体验和业务指标冲突时如何取舍。
- 我用 STAR 结构讲了推荐流去重服务的优化。当时通过调整架构和缓存策略降低了接口延迟与系统负载，并用优化前后的数据对比说明效果。面试官随后追问了技术选型和取舍依据。
- Round 2：Coding
- 题目要求计算棋子在棋盘上的可达位置，共分三步。
- 第一步实现皇后的移动，沿横、竖和对角线扫描；第二步加入障碍物，用 HashSet 保存坐标，某个方向遇到障碍物后立即停止；第三步支持 Queen、Bishop 和 Rook，根据 pieceType 配置不同方向，其余扫描逻辑共用。
- 建立障碍物集合需要 O(b)，方向扫描需要 O(n)，总时间复杂度为 O(n+b)。
- Round 3：System Design
- 第一题是广告事件聚合。广告事件包含 adId 和 servingId，用户事件包含 servingId、点击或曝光行为以及地区，要求按 (adId, action, region) 生成 Dashboard。方案是用 Kafka 接收事件，Flink 完成流式 Join 和聚合，Redis 保存 servingId 映射，结果写入 OLAP 数据库。
- 第二题是商品目录批量上传，单次最多 50 万件商品。更合理的设计是先把文件上传到对象存储，再通过任务 ID 异步解析、校验和批量入库，客户端可以查询进度并重试失败数据。这题提醒我，数据库选型前要先问清读取频率、更新方式和一致性要求。
- Round 4：Coding
- 题目给出一组被打乱的车票，每张票记录出发地和目的地，要求恢复完整路线。
- 用 Map 保存出发地到目的地的映射，再用 Set 记录所有目的地。没有出现在目的地集合中的出发地就是起点，之后沿映射依次还原路线。
- Follow-up 讨论了重复出发地、路线成环、多条不连通路线以及车票未全部使用等边界情况。
